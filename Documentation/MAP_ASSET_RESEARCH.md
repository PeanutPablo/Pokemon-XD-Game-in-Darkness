# MAP_ASSET_RESEARCH.md

Audit of map/navigation-relevant assets across five already-cloned community repositories, in service of one question this project cares about above all others: **can any of this data be trusted as a source of collision/walkability information for a future navigation-guidance feature, or is it visual-only?** Investigation date: 2026-07-24.

Repos audited (paths relative to `Research/ThirdParty/`, except `Pokemon-XD-Code` which is at the project root — see [REPOSITORY_AUDIT.md](REPOSITORY_AUDIT.md) for clone provenance/commit hashes of all six):

- `Blender-Addon-Gamecube-Models/` (model importer/exporter, most actively maintained)
- `Pokemon-XD-Code/` ("GoD Tool", Swift — turned out to be the single richest source for this audit by far)
- `XDscriptTools/` (script disassembler, Python)
- `pokemon_fsys_tool/` (FSYS archive tool, C++)
- `pokemon-ngc-rando/` (randomizer, C#)

This document deliberately reuses and cross-references, rather than duplicates, prior findings in [ARCHITECTURE_CODEMAP.md](ARCHITECTURE_CODEMAP.md) §11 ("Maps, rooms, doors, warps, collision, NPCs, and interactable objects") and [ACCESSIBILITY_HOOKS.md](ACCESSIBILITY_HOOKS.md) Tier 3 item 8, both scoped to `xd-decomp`/`Pokemon-XD-Code` only. This pass goes deeper into `Pokemon-XD-Code`'s actual struct-parsing code (not just symbol names) and adds the other four repos, which turned out to contribute little beyond `Pokemon-XD-Code` for this specific topic.

**Standing caveat, inherited from every other document in this project:** everything below describes **vanilla Pokémon Colosseum/XD (US)**, reverse-engineered by community tooling. Pokémon XG is an unknown-revision ROM hack. Map/room/collision data — especially anything involving added or altered areas — is exactly the kind of content a hack is likely to change. Nothing here should be assumed to apply to XG without direct verification (see [UNKNOWNS_AND_BLOCKERS.md](UNKNOWNS_AND_BLOCKERS.md)).

## 0. The file-type map (read this first — it's the skeleton everything else hangs off)

**Confirmed**, and independently cross-corroborated by two unrelated projects — `Pokemon-XD-Code/enums/XGFileTypes.swift:11-33` and `pokemon_fsys_tool/pokemon_fsys_tool.cpp:73-98` (`known_file_types` table) agree on the numeric type IDs and meanings for every entry below:

| Type ID | Extension | Category | What it holds |
|---|---|---|---|
| 0x02 (fsys tool: 1) | `.rdat` | **Visual render geometry** | "Room model in hal dat format" — the map/room's 3D visual mesh, same underlying HAL DAT format as character models. `Pokemon-XD-Code/enums/XGFileTypes.swift:13,139` |
| 0x04 | `.dat` | **Visual render geometry** | Character/object model, same DAT format |
| 0x06 (fsys tool: 3) | `.ccd` | **Collision geometry + trigger volumes** | "A 3d mesh which determines which parts of the map the player can or can't walk on/through for collision detection. Also marks special regions which can trigger script events like doors, warps and textboxes. Has an associated `.rdat` file." — `XGFileTypes.swift:15,141`, verbatim |
| 0x0e | `.scd` | **Script bytecode** | Per-room script, referenced by room's FSYS basename |
| 0x18 | `.cam` | **Camera coordinates** (+ optional light data) | Scene camera position/target/FOV, `XGFileTypes.swift:23`; also directly confirmed by the Blender addon's own format docs (§4 below) |
| 0x1c | `.rel` | **Mixed: script-linkage table + per-room runtime-adjacent structural data** | Holds warp-entry-point coordinates, NPC/character placement, room ID, group ID — see §2 |

The load-bearing fact from this table: **collision geometry (`.ccd`) and visual render geometry (`.rdat`) are two separate files**, connected only by a **documented naming/pairing convention** ("has an associated `.rdat` file"), not by shared vertex data. See §5 for exactly how far that connection can be trusted.

## 1. Map / room identification

**Category: static lookup data (not runtime, not visual, not script).**

- **Confirmed:** Two-tier naming. A "map" is a broad area (e.g. Phenac City), a "room" is one specific interior/exterior space within it. Map codes are a fixed enum of 19 entries — `Pokemon-XD-Code/enums/XGMaps.swift:14-35` — e.g. `M1` = Phenac City, `D1` = Shadow Pokemon Lab, `S2` = Team Snagem's Hideout. **Cross-project corroboration:** `pokemon-ngc-rando/Common/PokemonDefinitions/Maps.cs:7-30` defines the identical 19-entry list independently (different repo, different language, C# enum with matching names in matching order) — strong agreement, not just one project's claim.
- **Confirmed:** Room name convention derives from map code — `XGRoom.map` computed property takes the first two characters of the room name and looks it up against `XGMaps` (`Pokemon-XD-Code/Objects/data types/enumerable/XGRoom.swift:66-69`). A real room-name corpus exists at `Pokemon-XD-Code/JSON/XD/Room IDs.json` (e.g. `"0x63": "M1_houseC_1F"` — Phenac City, house C, ground floor).
- **Confirmed:** Room ID is a 2-byte value stored in a fixed-size struct array inside `common.rel`, at struct offset `0x2` (XD US/EU) — `Pokemon-XD-Code/Objects/data types/enumerable/XGRoom.swift:19-25` (`kRoomIDOffset`), struct size `0x40` bytes (XD non-JP) — `XGRoom.swift:11-17` (`kSizeOfRoom`). **Cross-project corroboration:** `pokemon-ngc-rando/Common/PokemonDefinitions/XD/Room.cs:11-16` independently states `RoomIDOffset = 0x2`, `NameIDOffset = 0x18`, and stride `64` bytes (`index * 64` = `0x40`) — exact numeric agreement with the Swift tool, from a wholly separate C# codebase.
- **Confirmed:** Each room struct also carries a `groupID` (`kRoomGroupIDOffset`, `XGRoom.swift:35-41`) identifying which FSYS archive holds that room's files, and a `nameID` (a string-table index for the human-readable in-game location name) at `kRoomNameIDOffset` (`XGRoom.swift:27-33`).
- **Runtime-address category (Confirmed, symbol/address only, no source body, vanilla XD US):** [ARCHITECTURE_CODEMAP.md](ARCHITECTURE_CODEMAP.md) §11 already documents a live "current room ID" memory address, `0x80814ab6` (XD), sourced from `Pokemon-XD-Code`. This is the one *runtime* room-identification data point found anywhere in this audit; everything else in this section is static, on-disk lookup data.

## 2. Scene hierarchy, object/model transforms, position/rotation/scale

**Category split matters a lot here — three genuinely different kinds of "position" exist in this data, and conflating them would be a mistake:**

### 2a. Warp entry-point coordinates (script/trigger-target coordinates, static/on-disk)

- **Confirmed:** `XGMapEntryLocation` — `Pokemon-XD-Code/XDRelIndexes.swift:377-426` — a fixed 0x10-byte record per room-entry-point, stored inside that room's `.rel` file: `angle` (u16, offset 0x0), `x`/`y`/`z` (each a big-endian 32-bit float, offsets 0x4/0x8/0xC). These are **the coordinates the player is placed at when warping into a room via a specific numbered entry point** — read from the room's REL via `XGMapRel.entryLocations` (`Objects/file formats/XGMapRel.swift:33,55-63`). This is exactly the kind of "spawn point" data a navigation-guidance feature would need as a stable, known-good target coordinate.
- **Category: script/warp-target coordinates**, not live runtime state and not render geometry — these are read once at room-load time to place the hero.

### 2b. NPC/character placement (static per-room table, loaded into runtime state)

- **Confirmed:** `XGCharacter` — `Pokemon-XD-Code/Objects/data types/XGCharacter.swift:11-182` — fixed 0x24-byte record per character, per room-REL: `xCoordinate`/`yCoordinate`/`zCoordinate` (floats, offsets `0x18`/`0x1C`/`0x20` — `kXOffset`/`kYOffset`/`kZOffset`, lines 20-22), `angle` (signed 16-bit, offset `0x4`), `characterID` (offset `0x8`), `model` index (offset `0x6`), `hasScript`/`scriptIndex` and `hasPassiveScript`/`passiveScriptIndex` (interactable-vs-ambient script hooks, offsets `0x14`/`0x16`/`0x10`/`0x12`), `movementType` (top 3 bits of the byte at offset `0x1`), and a visibility flag (top bit of the byte at offset `0x0`). Sanity-check bounds exist in the parser itself (`xCoordinate`/`yCoordinate`/`zCoordinate` > 2000 ⇒ `isValid = false`, lines 141-149) — an incidental but useful confirmation of the map's rough coordinate-space scale (single/double-digit-thousands units, not e.g. millions).
- **Cross-referenced, same struct, independently re-derived:** `Pokemon-XD-Code/Objects/struct tables/RoomsTable.swift:133-157` (`roomCharactersStruct`) describes the identical fields via the tool's generic struct-table system, and additionally documents bitflags not named in `XGCharacter.swift` directly: `Is Visible`, `Load Init?`, **`Is Collision Enabled`**, `Is Head Tracking Enabled`, `Is Interactable Through Walls` (lines 134-143). The `Is Collision Enabled` flag is notable: it confirms NPCs have a *per-character* collision toggle, separate from the map's static collision mesh.
- **Category: static per-room placement data**, loaded into a live runtime table at room load (`RoomsTable.swift:17-19` documents the room struct's runtime-filled `Character Data` pointer — see §2c).

### 2c. The room struct's runtime pointer fields (confirms static-vs-runtime split, not new data)

- **Confirmed:** `Pokemon-XD-Code/Objects/struct tables/RoomsTable.swift:11-27` documents the **retail binary's live in-memory room struct** (as opposed to the on-disk `common.rel` room table) with fields explicitly annotated `"Set at runtime while it's the current room"`: `Map File ID`, `Render Data` (pointer, "lighting and shadows"), `Character Data` (pointer), **`Warp Point Data`** (pointer), `Camera Data` (pointer). This struct is populated only for the *currently loaded* room — i.e., a companion tool cannot read "warp point data" or "character data" for an arbitrary room out of live memory unless that room is the one currently loaded. This matters directly for the vertical-slice design in the companion document: **the addresses these pointers resolve to are only valid while standing in that specific room.**
- **Category: runtime pointer table**, not itself position data — a structural fact about *how* the static per-room data (§2a/§2b) gets attached to the live game state.

### 2d. Visual scene hierarchy / model transforms

- **Confirmed, but not map-specific:** the Blender addon's IR (Intermediate Representation, `Blender-Addon-Gamecube-Models/shared/IR/`) and its DAT-format documentation (`technical-docs/file_formats.md`) describe bone/joint hierarchies, per-node transforms, and animation keyframes for the general HAL DAT model format — this applies identically whether the DAT is a `.rdat` room model or a `.dat` character/object model. **No room-specific or map-specific scene-graph concept exists in this addon** — it treats a room's visual geometry exactly like any other model file (confirmed by `technical-docs/compatibility_table.md:107`: `.rdat` is handled as "Raw DAT bytes... Pass-through", identical code path to `.dat`).
- **Unknown:** whether a room's `.rdat` visual mesh has any internal substructure (e.g. named sub-meshes per building/section) that could be useful for narration — not documented anywhere in the addon's technical docs, and not something this audit parsed directly (would require opening an actual `.rdat` file, which requires extracted game assets not present in this research-only pass).

## 3. Cameras

**Category: camera coordinates**, and this one is unambiguous and directly confirmed by the actively-maintained Blender addon's own reverse-engineered format spec, independent of `Pokemon-XD-Code`:

- **Confirmed:** `.cam` files are standard HAL DAT containers with a `SceneData` root holding `CameraSet` and `LightSet` nodes — `Blender-Addon-Gamecube-Models/technical-docs/file_formats.md:438-485`. A `CameraSet.camera` node has `position` (static eye vec3), `interest` (static target vec3), `field_of_view`, `roll`, `near`/`far` clip planes, and `viewport`/`scissor` (both 640×480 — confirming these are the actual GameCube render-camera parameters, not some abstract/logical value). Optional `CameraAnimation` entries hold eye/target position keyframes and FOV/roll/clip keyframes (`file_formats.md:449-485`).
- **Confirmed (`Pokemon-XD-Code`):** the room struct's `Camera Data` pointer (§2c) is filled at runtime, and `.cam` files are dispatched per-room via the same FSYS-basename convention as other room-type files (`XGFileTypes.swift:23`, type ID `0x18`).
- **Important distinction for a navigation feature:** this is the **scene/cutscene render camera** (what the TV screen shows), not the player's logical facing/orientation. There is no confirmed link anywhere in this audit between `.cam` camera data and player facing — camera and player-facing are independently-tracked concepts in essentially all 3D games of this era (fixed or scripted camera angles are extremely common in this genre), and nothing found here contradicts or confirms that for this specific engine.

## 4. Doors and warp triggers

**Category: mostly trigger volumes (script-activated zones); door *animation* is visual, door *gating logic* is not.**

- **Confirmed — the interaction-point system**, `Pokemon-XD-Code/XDRelIndexes.swift:11-449` (`XGInteractionPointData`, `kSizeOfInteractionPoint = 0x1C`): a fixed-size static table in `common.rel` (`CommonIndexes.InteractionPoints`, index 62 — `XDRelIndexes.swift:104-105`), where each 0x1C-byte entry has an `interactionMethod` (`XGInteractionMethods` enum: `None`/`WalkThrough`/`WalkInFront`/`PressAButton`/`PressAButton2(Colosseum only)` — `XDRelIndexes.swift:47-68`), a `roomID` this point belongs to, a `regionIndex` linking it to a specific collision-mesh region (see §6), and a payload that dispatches to one of: `Warp(targetRoom, targetEntryID, sound)`, `Door(id)`, `Text(stringID)`, `Elevator(elevatorID, targetRoomID, targetElevatorID, direction)`, `CutsceneWarp(targetRoom, targetEntryID, cutsceneID, cameraFSYSID)`, `PC(roomID, unknown)`, or a generic script-function call (`XDRelIndexes.swift:78-113`). This is **the single richest, most directly navigation-relevant structure found in this entire audit** — it is the authoritative, static, on-disk list of every door/warp/PC/textbox trigger in the game, each tagged with its room, its interaction method (walk-through vs. walk-in-front vs. press-A), and — for warps specifically — its exact target room and target entry point ID (which resolves via §2a to an actual x/y/z spawn coordinate).
- **Confirmed — doors as a separate, second table:** `XGDoor` — `Pokemon-XD-Code/Objects/data types/enumerable/XGDoor.swift:19-68` (`kSizeOfDoorData = 0x18`, `CommonIndexes.Doors` index 60) — `roomID`, `identifier`, and a `fileIdentifier` pointing at "the `.rdat` model, last byte is the index for the door animation in that model" (`Objects/struct tables/RoomsTable.swift:110`). **This is a second, genuine, code-documented render↔collision-adjacent link**: a door *trigger* (interaction point, §above) references a door *ID* (this table), which in turn references a specific animation index inside the room's **visual** `.rdat` model — i.e., "open this door" is confirmed to mean "play animation N on the room's render mesh," a real cross-file connection, distinct from and in addition to the walkability question in §5-6.
- **Refining a prior claim in this project's own documentation:** [ARCHITECTURE_CODEMAP.md](ARCHITECTURE_CODEMAP.md) §11 states "no 'warp' (teleport) symbols were found by name in `xd-decomp`'s `symbols.txt`." This audit found `floorLink = .text:0x801202E0` and `floorLinkWithSE = .text:0x80120304` (`xd-decomp/config/GXXE01/symbols.txt:4828-4829`, symbol+address only, no decompiled body). `Pokemon-XD-Code`'s own inline comment names the corresponding common-script function `@floor_link` as the handler for interaction-point type `kIPWarpValue = 0x4` (`XDRelIndexes.swift:39,135`, `Objects/data types/enumerable/XGInteractionPoint.swift` region). **Inferred, not Confirmed:** `floorLink`/`floorLinkWithSE` in `xd-decomp` and the script-callable `@floor_link` function documented by `Pokemon-XD-Code` are the same underlying engine routine — the naming match is a strong signal but neither project's source independently proves the two are identical (same caution `ARCHITECTURE_CODEMAP.md:87` already applies to "room" vs. "floor" terminology generally). This does *not* invalidate the prior "no literal 'warp' substring" observation — it refines it with a same-concept-different-name candidate.

## 5. Visual render geometry vs. collision geometry — the relationship, stated as precisely as the evidence allows

This is the question the project instructions specifically told me to answer carefully, so stating it plainly:

- **Confirmed, named/documented pairing, NOT shared vertex data:** `Pokemon-XD-Code/enums/XGFileTypes.swift:141` states the `.ccd` (collision) format "has an associated `.rdat` file" (visual). Additionally, `XGCollisionData`'s own loader **actively looks up a same-basename file of a different type** — `Objects/file formats/XGCollisionData.swift:67-70`: `let relFile = XGFiles.typeAndFsysName(.rel, self.file.fileName.removeFileExtensions())` — i.e., given a `.ccd` file, the tool constructs the filename of the room's `.rel` file by swapping the type and keeping the same base name, and loads it (`XGMapRel(file: relFile, ...)`). This confirms, **in actual working code**, that collision files, REL files (§2a/§2b data), and — per the FSYS convention documented throughout `XGFileTypes.swift` — `.rdat`/`.scd`/`.cam` files for the same room all share **one base filename across different type-tagged files inside one FSYS archive group**. This is a real, code-verified linkage.
- **What this linkage does *not* establish:** no code anywhere in `Pokemon-XD-Code`, the Blender addon, or any of the other three repos was found that loads a room's `.rdat` visual mesh and its `.ccd` collision mesh into a shared vertex buffer, compares their geometry, or treats them as the same mesh at different LOD. The Blender addon imports `.rdat` purely as generic HAL DAT visual geometry (§2d) and has **zero code path for `.ccd`/collision at all** — confirmed by an exhaustive grep of `Blender-Addon-Gamecube-Models/technical-docs/` for collision/warp/door/room/NPC terminology (found only unrelated hits: TEV-chain "material collision," bone-index-collision-avoidance in the exporter, and NPC references confined to the animation sub-system, e.g. `technical-docs/exporter_setup.md:339,387,403,527` — none referring to collision meshes).
- **Direct, load-bearing statement for this project's navigation-guidance goal:** it is common in games of this era (and explicitly typical of the HAL/GameCube engine family this game shares lineage with, per the Blender addon's own README) for collision meshes to be deliberately simplified relative to visual meshes — fewer triangles, different topology, sometimes entirely different bounding proxies for complex visual detail (railings, furniture, decorative geometry). **Nothing found in this audit confirms or refutes whether that simplification happens here.** Per this project's standing instruction: **this must be treated as Unknown, not Inferred.** The correct, verified statement is: *`.ccd` collision files are the actual walkability data — confirmed by the tool's own documentation and by the actual triangle/trigger structure parsed in §6 — and `.rdat` visual files are a separately-stored, same-room-associated but not geometry-identical file. A navigation feature must read `.ccd` data (or a live equivalent), never `.rdat`/visual geometry, for walkability.*

## 6. Collision meshes, walkable polygons, bounding boxes, trigger volumes

**Category: collision geometry AND trigger volumes together — genuinely the same file format, distinguished per-triangle.** This is the most important single finding of this audit.

- **Confirmed — full structural parse exists in working code:** `XGCollisionData` — `Pokemon-XD-Code/Objects/file formats/XGCollisionData.swift:11-166`. Reading a `.ccd` file:
  - A list-header at file start gives `list_start` and `entry_count` (`getWordAtOffset(0x0)`/`getWordAtOffset(0x4)`, lines 72-73).
  - Each of `entry_count` "sections" is a fixed 0x40-byte record (`entry_size = 0x40`, line 80); within it, a scan from offset `0x24` to `0x40` in 4-byte steps (line 84) finds up to seven populated sub-pointers. **The specific sub-offsets `0x2C` and `0x30` are hard-coded as marking interactable geometry** (line 89: `if o == 0x2c || o == 0x30 { isInteractable = true }` — code comment: "this is a warp point, door, pc, etc.").
  - Each populated sub-pointer leads to a run of triangles (`face_size = 0x34` bytes each, line 97): three vertices (3×3 floats = 3×0xC bytes, lines 117-133) plus one normal vector (0xC bytes, lines 135-137), plus a 16-bit `type` and a 16-bit `interactionIndex` per triangle (lines 108-112) — **the byte offset of `type` vs. `interactionIndex` within the triangle record actually swaps depending on which of the two interactable sub-offsets (`0x2C`/`0x30`) the triangle run came from** (line 108-109: `typeOffset = o == 0x30 ? 0x32 : 0x30`), a real, easy-to-miss asymmetry in the format.
  - **This is the confirmed, direct, code-level link between collision geometry and trigger volumes the project instructions asked me to look for**: interactable triangles (`isInteractable == true`) carry an `interactionIndex` that is the same index space as `XGInteractionPointData.interactionPointIndex` (§4) — i.e., a specific triangle (or set of triangles) in the collision mesh **is** a specific door/warp/PC/textbox trigger region, not a separate, disconnected volume. `XGVertex` (`GoDToolOSX/Objects/XGVertex.swift:15-73`) carries `isInteractable`, `interactionIndex`, and `type` per-vertex for exactly this reason, confirming the tool's own 3D collision viewer (`GoDToolOSX/View Controllers/GoDCollisionViewController.swift`, gated behind macOS/Metal/Cocoa — see §7) is built to highlight these regions directly on the mesh.
  - **Non-interactable triangles still carry a `type` field** (lines 111,143,149-151 collect all observed `type` values into a global `types` list) — this is almost certainly a walkable-surface-type tag (e.g. grass/water/ledge/wall), consistent with the file-type description "determines which parts of the map the player can or can't walk on/through." **Unknown:** the actual meaning of each numeric `type` value — no enum, lookup table, or comment maps `type` codes to named surface behaviors anywhere in this codebase. This would need direct correlation against known in-game surfaces (e.g. "value X only appears under known water tiles") to resolve, which is out of scope for a read-only research pass with no extracted game files.
- **Confirmed — bounding/scale fact:** the collision loader tracks `maxD`, the largest absolute coordinate value seen across all vertices in a file (line 75, updated lines 130-132), and uses it purely to normalize vertex coordinates for the tool's own 3D viewer (`scale(maxD:magnification:)`, `XGVertex.swift:63-72`) — **this is a display-only normalization, not a semantic bounding-box/AABB concept**, and should not be mistaken for a stored per-room bounding box (no such stored bounding-box field was found in this format).
- **No standalone "bounding box" or dedicated "trigger volume" struct exists separately from the collision-triangle format above** — in this engine, a trigger volume literally *is* a subset of collision triangles flagged interactable, not a separate axis-aligned-box or capsule-volume primitive. Flag this explicitly since it differs from many other engines' conventions (where trigger volumes are typically simple separate primitives, not mesh-embedded flags).

## 7. Navigation nodes / map connections

- **Unknown / does not appear to exist as a distinct concept.** No pathfinding graph, navmesh, waypoint list, or room-adjacency table was found in any of the five repos. The closest things to "map connections" are:
  - The warp-target fields inside `XGInteractionPointData.Warp`/`.CutsceneWarp`/`.Elevator` (§4) — these establish *which rooms connect to which via which specific triggers*, which is graph-like (room A, trigger at collision-region N → room B, entry point M) but is reconstructed from the trigger table, not a first-class "map graph" data structure the game itself stores.
  - `RoomBGM` (`CommonIndexes.RoomBGM`, index 64, `Pokemon-XD-Code/XDRelIndexes.swift:106-107`) and other per-room static tables are lookup tables keyed by room ID, not connectivity graphs.
- For the one-room vertical slice proposed in [NAVIGATION_VERTICAL_SLICE.md](NAVIGATION_VERTICAL_SLICE.md), the room-to-room graph is not needed (explicitly out of scope there too) — only the warp-trigger → target-entry-point → coordinate chain within and immediately adjacent to a single room, which *is* fully confirmed above (§2a + §4).

## 9. Runtime hero position/facing — a promising, previously-undocumented lead

Not explicitly one of the requested checklist categories, but directly load-bearing for the navigation-experiment design in the companion document, and newly found in this pass (not previously listed in [ACCESSIBILITY_HOOKS.md](ACCESSIBILITY_HOOKS.md) item 9, which currently says "no live player-position address found in either repo"):

- **Confirmed (symbol+address only, vanilla XD US `GXXE01`, `xd-decomp`, zero decompiled source bodies — Needs-discovery-grade lead, not a proven address):**
  - `heroMoveGetHeroPos = .text:0x801501D4` (size 0x38) and `heroMoveGetHeroRot = .text:0x8015019C` (size 0x38) — global-scope (unmangled/exported) accessor functions — `xd-decomp/config/GXXE01/symbols.txt:6606-6607`.
  - Their mangled internal counterparts `getPos__FP5GSvec15HEROMOVE_MEMBER` / `setPos__F15HEROMOVE_MEMBERP5GSvec` (`symbols.txt:6604-6605`) and `getRot__FP5GSvec15HEROMOVE_MEMBER` / `setRot__F15HEROMOVE_MEMBERP5GSvec` (`symbols.txt:6602-6603`) confirm the position accessor's signature takes/returns a `GSvec` (the engine's vector type, consistent with the `Vector` scripting class documented independently in `XDscriptTools/XDscriptLib/FunctionInfo.py:198-220` — `crossProduct`/`dotProduct`/`norm`/`angle` methods, a different but corroborating piece of evidence that this engine has one consistent vector-math primitive used from both native code and script bytecode).
  - `HeroMove = .bss:0x804479F0` (size `0x660`, `symbols.txt:16475`) — the live, fixed-address `HEROMOVE_MEMBER` struct instance these accessors operate on. A large (1,632-byte) always-resident struct at a static address is a strong candidate for containing the actual live, continuously-updated player position/rotation, reachable without any pointer-chasing — exactly the shape of address a Route B (external memory-polling) companion needs.
  - `init_hero_pos = .bss:0x804E0AB0` (size `0xC` = 3 floats) and `init_hero_rot = .bss:0x804E0ABC` (size `0xC`) — `symbols.txt:16670-16671`. **Named "init_", not "current_"** — Inferred, not Confirmed, that these hold a one-time spawn value (set once when entering a room from a warp entry point, §2a) rather than a continuously-updated live position. This distinction matters enormously for a polling companion: if these are write-once-per-room-load, they are useless for continuous position tracking and only `HeroMove` (or fields within it) would work.
- **Unknown, and the actual next step:** the exact byte offset of position/rotation *within* the 0x660-byte `HeroMove` struct, whether `heroMoveGetHeroPos`/`heroMoveGetHeroRot` read directly from a fixed offset in that struct or via further pointer indirection, and — as with everything else in this document — whether any of these XD-US addresses survive unchanged in XG. **This is now the single best-supported starting hypothesis for the Phase 0 memory-discovery experiment**, better than a blind scan, but still requires empirical confirmation exactly like the title-menu-cursor and HP leads already tracked in [ACCESSIBILITY_HOOKS.md](ACCESSIBILITY_HOOKS.md).

## 10. Does the Blender addon's CLI run headlessly, without Blender's GUI? (Direct answer, read from actual code)

**Confirmed — yes, for the import/parse side, with one caveat; the export side was not verified to have an equivalent standalone CLI entry point.**

- `Blender-Addon-Gamecube-Models/CommandLineInterface.py:1-48` is a plain Python script (`import os`, `import sys`, no Blender-only imports at module scope).
