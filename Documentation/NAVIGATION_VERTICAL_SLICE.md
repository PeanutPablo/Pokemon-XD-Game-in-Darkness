# NAVIGATION_VERTICAL_SLICE.md

Design (not implementation) for the smallest possible overworld-navigation experiment: guide a blind player, via NVDA, from one known stable point inside a single small interior room to one specific doorway in that same room. This document is the navigation-domain counterpart to [FIRST_VERTICAL_SLICE.md](FIRST_VERTICAL_SLICE.md) (which targets battle-menu narration) — same "smallest possible slice" philosophy, same Route B architecture (external Windows companion reading unmodified Dolphin's memory via `dolphin_memory_engine`, per [IMPLEMENTATION_ROUTE_COMPARISON.md](IMPLEMENTATION_ROUTE_COMPARISON.md)), applied to a different, harder problem: moving the player through space, not just reading a menu index.

**This document explicitly does NOT attempt whole-game pathfinding, room-to-room routing, or general overworld navigation.** Every design decision below is scoped to one room, one starting point, one destination doorway. See "What this slice deliberately does not do" at the end.

**Standing caveat, same as every other document in this project:** the room/asset data below is drawn from vanilla Pokémon XD (US, `GXXE01`), reverse-engineered by community tools (`Pokemon-XD-Code`) and cross-referenced against `xd-decomp` symbols. None of it is verified against Pokémon XG, an unknown-revision ROM hack. Every address, offset, and struct layout referenced here must be treated as a **hypothesis to test against XG**, not a fact about XG. See [UNKNOWNS_AND_BLOCKERS.md](UNKNOWNS_AND_BLOCKERS.md) and [MAP_ASSET_RESEARCH.md](MAP_ASSET_RESEARCH.md) (the audit this design is built on).

---

## 1. Select one small interior room

**Candidate: `M1_houseC_1F`** — Phenac City, house C, ground floor.

- **Confirmed to exist as a named room ID** in the community-maintained room table: `"0x63": "M1_houseC_1F"` — `Pokemon-XD-Code/JSON/XD/Room IDs.json`. Room ID `0x63` (99 decimal).
- **Inferred, not Confirmed, that it is actually small/single-space:** this is a naming-convention inference (`_1F` = first floor of a small named house, part of a `houseA`/`houseB`/`houseC`/`houseD` set typical of a small town — `Room IDs.json` lines listing `M1_houseA_1F`, `M1_houseA_2F`, `M1_houseB_1F`, `M1_houseC_1F` together, `Pokemon-XD-Code/JSON/XD/Room IDs.json`). **This has not been visually confirmed** by opening the room in Dolphin or extracting its `.rdat`/`.ccd` files — that confirmation is Step 1 of the actual experiment (§7 below), not something this design document can state as fact. If house C turns out to be a bad choice (e.g., unusually large, multi-level, or containing NPCs that block a clean test), any of the other single-floor `houseA`–`houseD` rooms in `M1` (Phenac City), `M2` (Pyrite Town), `M3` (Agate Village), or `M6` (Gateon Port) — all listed in `Room IDs.json` — are equally valid substitutes chosen for the same reason: small, named, single-purpose.
- **Why a house interior specifically, not an outdoor area or a story-critical room:** interiors have a bounded, small collision mesh (fewer triangles to reason about, per `MAP_ASSET_RESEARCH.md` §6), a small, enumerable set of doors/warps (usually just the entrance/exit), and — being a generic unnamed NPC's house rather than a story location — low risk of complex scripted events firing mid-test and disrupting a controlled trial.

## 2. Identify its map ID

- The room's **map** (broad area) is `M1` = Phenac City — derived from the room-name prefix convention, `XGRoom.map` (`Pokemon-XD-Code/Objects/data types/enumerable/XGRoom.swift:66-69`), cross-referenced against the `XGMaps` enum (`Pokemon-XD-Code/enums/XGMaps.swift:14-35`).
- The room's **room ID** is `0x63`, its **group ID** (which FSYS archive holds its files) is a separate field read directly from the room's struct entry in `common.rel` at runtime — `kRoomGroupIDOffset` (`XGRoom.swift:35-41`) — and is **not yet known for this specific room** without actually running the extraction tooling against a real ISO, which this read-only research pass did not do (no game files were extracted; see `MAP_ASSET_RESEARCH.md` for why: this is asset-format research, not asset extraction).
- **Concrete first action of the real experiment (not yet performed):** run `Pokemon-XD-Code`'s GoD Tool (or its CLI variant, per `Pokemon-XD-Code/CLI Compilers/`) against your own XG ISO, look up room ID `0x63` (or whichever room is actually confirmed small — see §1), and record its resolved group ID and FSYS archive name. This step also **immediately answers whether the vanilla room-ID/room-name mapping means anything for XG at all** — if XG's `common.rel` room table doesn't contain a room at the same ID with a recognizable name, that's the first, cheapest possible signal that XG has restructured its room table, before any deeper work is invested.

## 3. Extract its script and relevant assets

**Not performed in this design pass** (no XG ISO available to this research task) — this section specifies exactly what extraction would need to produce, so the real experiment has a checklist:

- The room's `.scd` script file (dispatched via the FSYS-basename convention documented in `MAP_ASSET_RESEARCH.md` §0/§5 — same base filename as the room's `.rdat`/`.ccd`/`.rel`/`.cam`, different type suffix). `Pokemon-XD-Code`'s script decompiler converts `.scd` → human-readable `.CMS`/`.XDS` text (`Pokemon-XD-Code/enums/XGFileTypes.swift:148`).
- The room's `.rel` file, parsed via `XGMapRel` (`Pokemon-XD-Code/Objects/file formats/XGMapRel.swift:10-113`) to enumerate: `roomID`, `groupID`, `characters` (NPC list, §4 below), `entryLocations` (warp/spawn coordinates, §4 below), and any `treasure` entries for this room.
- The room's `.ccd` collision file, parsed via `XGCollisionData` (`Pokemon-XD-Code/Objects/file formats/XGCollisionData.swift:11-166`) to enumerate every triangle, its `type`, and — critically — every triangle flagged `isInteractable` along with its `interactionIndex` (this is how §5's door/trigger list gets cross-referenced against actual walkable-mesh geometry, not just the abstract interaction-point table).
- Optionally, the room's `.rdat` visual model, importable via the Blender addon's CLI (confirmed headless-capable for the parse/describe/plan phases without any Blender GUI — `MAP_ASSET_RESEARCH.md` §10) purely as a **sighted-assistant cross-check** during design/debugging of this experiment (e.g., a sighted collaborator visually confirms room layout against the numeric data) — never as a source of collision truth for the companion itself (see the render-vs-collision distinction in `MAP_ASSET_RESEARCH.md` §5).

## 4. Enumerate known doors/NPCs/interactables

From the extracted `.rel` and `.ccd` data (§3), for the chosen room, the experiment must build a short table like this (values are placeholders — the real experiment fills these in from the actual extracted room):

| Item | Source | Fields to record |
|---|---|---|
| Entry/spawn point(s) | `XGMapRel.entryLocations` → `XGMapEntryLocation` (`Pokemon-XD-Code/XDRelIndexes.swift:383-426`) | index, x, y, z, angle — this is the **stable, known-good starting point** for the experiment (§6) |
| NPCs | `XGMapRel.characters` → `XGCharacter` (`Pokemon-XD-Code/Objects/data types/XGCharacter.swift:11-182`) | x, y, z, angle, `hasScript`/`scriptIndex` (is this NPC interactable), `movementType` (stationary vs. wandering — a wandering NPC is a *moving obstacle*, which the experiment should explicitly avoid routing through) |
| Doors/exits | `CommonIndexes.InteractionPoints` filtered to this room's `roomID`, `interactionMethod` + `.Door`/`.Warp` payload (`Pokemon-XD-Code/XDRelIndexes.swift:78-113,240-312`) | interaction method (walk-through / walk-in-front / press-A), target room, target entry point ID, and — via the door table — the animation index into the room's `.rdat` (`Pokemon-XD-Code/Objects/data types/enumerable/XGDoor.swift:19-68`) |
| Collision-flagged trigger regions | `XGCollisionData.interactableIndexes` cross-referenced by `interactionIndex` against the interaction-point table above (`Pokemon-XD-Code/Objects/file formats/XGCollisionData.swift:78-158`) | which specific collision triangles constitute each door/warp's actual walk-in/press-A region — this is what turns "there is a door" into "the trigger volume is this exact patch of floor" |

**Target for this slice: exactly one doorway** — pick the single interaction point in this table whose `interactionMethod` is `WalkThrough` or `PressAButton` (the two methods that correspond to an unambiguous, discrete "you have reached the door" event) and whose payload is `.Warp` (an actual room-to-room exit, as opposed to `.Text`/`.PC` which don't involve movement). If the chosen room has multiple exits, pick the one geometrically closest to the entry/spawn point identified above, to keep the guided path as short as possible for this first trial.

## 5. Find the player's live coordinates and facing

This is the least-certain part of the whole design, and is flagged as such deliberately.

- **Symbol/address leads exist, but are unverified** — see `MAP_ASSET_RESEARCH.md` §9 for the full citation trail. Summary: `xd-decomp`'s `symbols.txt` (vanilla XD US, `GXXE01`) names `heroMoveGetHeroPos`/`heroMoveGetHeroRot` (`.text:0x801501D4`/`.text:0x8015019C`) as accessor functions operating on a fixed-address, always-resident struct `HeroMove` (`.bss:0x804479F0`, size `0x660`). **No decompiled source body exists for any of these** — the symbol table gives names and addresses only, not what offset within the 0x660-byte struct actually holds x/y/z/facing, nor confirmation that the struct is continuously updated (as opposed to, e.g., snapshotted at intervals). A second, weaker lead — `init_hero_pos`/`init_hero_rot` (`.bss:0x804E0AB0`/`0x804E0ABC`, each 3 floats) — is explicitly named "init_", making it Inferred (not Confirmed) to be a one-time spawn value rather than a live position, and therefore a worse candidate for continuous tracking.
- **This means Phase 0 of [FIRST_VERTICAL_SLICE.md](FIRST_VERTICAL_SLICE.md)'s address-discovery method is required here too, before any of the rest of this design can run**, exactly as that document already establishes for the title-menu-selection case. The `HeroMove` struct address (`0x804479F0`) is a much better starting point for that discovery process than a blind full-memory scan would be: **the concrete first move is to open Dolphin's built-in memory viewer (or Dolphin Memory Engine) at `0x804479F0` in XG, walk the character around, and watch for 3 adjacent floats that visibly track world position** — this narrows the discovery search from "all of MEM1" to "one known 0x660-byte region," which is a meaningfully smaller and faster search than Phase 0 in the battle-menu document had to do (that one had no comparable struct-address lead at all).
- **Facing/orientation**: the same struct/accessor pair (`heroMoveGetHeroRot`/`getRot__FP5GSvec...`) is the equivalent lead for facing direction, on the working assumption (Inferred, not Confirmed) that "rotation" here means yaw/facing-angle rather than a full 3-axis rotation — plausible for a game where the player character only visibly rotates around the vertical axis while walking, but not independently proven by anything read in this pass.
- **Recovery if this lead doesn't pan out:** fall back to the same blind memory-search method (write-breakpoint scan or Dolphin Memory Engine value-search, moving the character and watching for changing values) already proven out conceptually for the menu-cursor case in `FIRST_VERTICAL_SLICE.md` Phase 0 — just without the head start `HeroMove`'s address gives.

## 6. Compare runtime coordinates against extracted object/script coordinates

Once §5 produces a trusted live x/y/z/facing address (or three separate addresses), and §3/§4 have produced the room's static entry-point and door-trigger coordinates:

- **The coordinate spaces must be checked for a shared reference frame before any comparison is meaningful.** The static per-room coordinates from `.rel` (entry points, NPCs, §2a/§2b in `MAP_ASSET_RESEARCH.md`) are room-local floats (the parser's own sanity bound of `> 2000 ⇒ invalid`, `Pokemon-XD-Code/Objects/data types/XGCharacter.swift:141-149`, gives a rough sense of scale but says nothing about origin placement). **Whether the live runtime position (§5) is expressed in that same room-local space, or in some other space (e.g. a world-space offset, or a space that resets differently on room load), is Unknown and must be empirically checked** — the simplest check: stand exactly on the room's recorded entry-point coordinate (walk to the door you just entered through and stand still) and see whether the live-memory reading matches that `.rel` entry-point value (within reasonable floating-point tolerance). If it doesn't match at all (wrong order of magnitude, wrong sign convention, or a completely different value range), the two coordinate systems are not directly comparable and a transform (or a different runtime address entirely) is needed before any guidance logic can work.
- **Once a shared frame is confirmed:** the single doorway target selected in §4 has a known static (x, y) footprint (from its collision-triangle region, `MAP_ASSET_RESEARCH.md` §6) or, more simply for a first pass, use the **target room's entry-point coordinate that this door warps *to*** as a rough proxy for "where the door is" is wrong — instead use the **source room's own collision-mesh trigger-region coordinates** (the actual door location in the room you're standing in), which is what `XGCollisionData`'s interactable-flagged triangles directly provide (§3/§4).

## 7. Guide the user from one stable start point to one doorway

**Design, not implementation.** Minimal viable guidance loop, deliberately simple:

1. **Stable start point:** the room's entry-point coordinate (§4) — i.e., where the player is placed immediately after warping in. The companion's first spoken/logged message on starting a guidance session should state that this is the assumed starting position, and should **not** trust it silently — see §8 recovery below for what happens if the player isn't actually there.
2. **Direction narration, not step-by-step pathfinding:** compute the vector from live player position to the target door's collision-trigger centroid (a simple 2D delta in x/z, ignoring y/height for a single-floor room). Convert that delta plus the player's live facing angle (§5) into a **relative** direction — "door is ahead," "door is to your left," "door is behind you" — using coarse buckets (e.g. 8-way: ahead / ahead-right / right / behind-right / behind / behind-left / left / ahead-left) rather than a precise bearing in degrees, since precise degree narration is not actionable for a blind user walking with a GameCube analog stick.
3. **Update cadence:** re-evaluate and re-speak the relative direction only when it changes bucket (same debounce principle as the menu-selection prototype in `FIRST_VERTICAL_SLICE.md` — avoid speaking every poll tick), plus a distance-based cue when the player crosses a small number of coarse distance bands (e.g. "far" / "getting closer" / "very close") so the player has some sense of progress without a constant stream of speech.
4. **Arrival:** when live position enters the door's actual collision-trigger region (§4/§6) — not a fixed radius guess, the real interactable-triangle region — speak a clear, distinct "door reached" cue, different from the directional cues, so it's unambiguous.
5. **No automated movement, ever.** This design only speaks directions; it never sends input, never touches the emulated controller state, and never writes to Dolphin's memory — consistent with every other design in this project (Route B is read-only by design, per `IMPLEMENTATION_ROUTE_COMPARISON.md`).

## 8. Recovery if the user turns incorrectly or collides

This is the piece that makes a one-room slice meaningfully different from the already-designed menu-selection prototype (that one has no concept of "the user is now in the wrong state" — a menu cursor can't get lost; a walking player can).

- **Wrong-turn recovery:** since guidance is direction-relative and re-evaluated continuously (§7.2-3), a wrong turn self-corrects on the next update — the companion doesn't need special-case "you turned wrong" logic, it just needs to keep re-computing and re-speaking the current correct relative direction as the player's live position/facing changes. The only design requirement this places on the polling loop: **it must never assume monotonic progress toward the goal** — a player moving away from the door is exactly as valid an input as one moving toward it, and the direction/distance narration must update correctly in either case without any "why did you go backward" special messaging (out of scope, and potentially confusing) for this first slice.
- **Collision recovery (the player is stuck against a wall/obstacle):** the design leans on the "distance getting closer" cue (§7.3) being **absent** as the implicit signal — if the spoken direction says "ahead" repeatedly but the distance band never improves over several update cycles despite the player apparently moving (holding a direction key), that's the natural in-band signal something is blocking progress. **Explicit collision detection (e.g. reading a "hero is currently blocked" flag) is not attempted in this design** — no such live flag was identified anywhere in this audit's citation trail (`MAP_ASSET_RESEARCH.md` documents `GScolsys2HitNpcCollision`/`GScolsys2HitCollision`/`checkHitCollision` as symbol-only, no decompiled body, in `ARCHITECTURE_CODEMAP.md` §11 — a Tier-3/needs-decompilation-grade lead, not a usable address). If real-world testing of this slice shows the "distance not improving" implicit signal is insufficient, a follow-up slice could investigate those collision-check symbols as actual read addresses, but that is out of scope for this first design.
- **"Where am I" recovery:** a companion this simple should support an on-demand repeat/re-orient key (mirroring the "non-conflicting repeat-current-selection key" already specified for the menu prototype in `FIRST_VERTICAL_SLICE.md`) that re-speaks the current relative direction and distance band immediately on request, rather than waiting for the next natural bucket-change — useful if the player got distracted, missed a cue, or just wants reassurance.
- **Total loss of tracking (player leaves the room, e.g. through a different door than the one being tracked to):** the companion should detect this by checking the live room-ID address (`MAP_ASSET_RESEARCH.md` §1, `0x80814ab6` for vanilla XD US — itself unverified for XG) against the expected room ID, and if it no longer matches, stop narrating directions for the old target and speak a clear "left the room" message rather than continuing to give directions that are now meaningless (the door's static coordinates are only valid while in the room they belong to).

## 9. Explicitly out of scope for this design

- **No whole-game pathfinding.** This design ends at one doorway. It has no concept of chaining multiple rooms, no room-adjacency graph (confirmed not to exist as a first-class data structure anyway — `MAP_ASSET_RESEARCH.md` §7), and makes no attempt to generalize beyond the single room chosen in §1.
- **No handling of moving NPCs as dynamic obstacles** beyond noting their existence and `movementType` in §4 — a wandering NPC blocking the path is a real possible failure mode this design does not attempt to solve.
- **No automated input/movement.** Same standing rule as every other companion design in this project (§7.5).
- **No attempt to resolve the `type` field's meaning in collision triangles** (`MAP_ASSET_RESEARCH.md` §6, flagged there as Unknown) — this slice only needs to know *which* triangles are the target door's trigger region, not what walkable-surface type any triangle represents.
- **No write access to game memory, anywhere in this design** — matches the standing rule already established for the battle-menu prototype.
- **No claim that the vanilla-XD room/coordinate/address data above is valid for XG** — restated one final time because it is the single most important caveat in this entire document: **every numbered step above that cites a specific room ID, address, or offset must be re-verified against an actual XG image before being trusted**, exactly as `FIRST_VERTICAL_SLICE.md` Phase 0 already requires for the menu-selection case.
