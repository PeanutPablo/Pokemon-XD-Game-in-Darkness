# ARCHITECTURE_CODEMAP.md

Consolidated code/symbol/data-structure map across both repositories, organized by the 14 categories requested. Every entry is labeled **Confirmed** (real decompiled source, or a resolved symbol+address, or a concretely-documented struct offset — I verified the citation exists), **Inferred** (a plausible name in a placeholder/comment/declaration with no body, or a structurally-derived-but-not-explicitly-stated value), or **Unknown** (nothing found). Addresses from `Pokemon-XD-Code` are **for unmodified retail XD US (GXXE) only** — see the version-scope warning at the end of this document before using any of them against XG.

Repos referenced: `xd-decomp/` (TeamOrre, primary) and `Pokemon-XD-Code/` (PekanMmd, secondary reference).

## Phase 0 runtime correction (2026-07-23)

- **Confirmed:** `_orreHero = 0x8043C930`, `_menuCtrlHero = 0x804B00A4`, and `g_pHero = 0x804EBBE0` are valid vanilla-XD symbols.
- **Refuted hypothesis:** the prior assumption that `_orreHero`, `_menuCtrlHero`, or the observed `g_pHero` target directly exposed the active battle Pokémon using the documented `Hero.partyPokemon[]` layout did not survive runtime inspection. The static objects remained zero and the observed pointer target had a repeating actor-like layout, not the expected `Pokemon` layout. Do not repeat this route without first establishing the owning type.
- **Inferred:** `0x804454B4` and `0x804454BC` mirrored the values 590, 170, 125, and 53 across the controlled Salamence-versus-Metagross observations. The final decrease was close to expected poison damage. This supports “active battler HP under those conditions,” but not a known owner, stable pointer chain, maximum-HP field, opponent field, restart stability, or XG compatibility.
- **Unknown:** the battle-command-menu highlighted selection remains the next discovery target. Relevant vanilla symbols include `menuFightMainCtrl = 0x8001D088`, `menuFightOpenTop = 0x8001E3E0`, and `menuFightStatus = 0x804EA728`, but none is yet a verified highlighted-index field.

## 13. Text encoding and string resources

- **Confirmed (real decompiled source, `xd-decomp`):** `src/dolphin/os/OSFont.c` (751 lines, complete) — `FontDataAnsi`/`FontDataSjis` pointers, `FontEncode`, `GetFontCode(u16 encode, u16 code)`, `OSGetFontEncode()`, `OSLoadFont(...)`, `OSGetFontTexel(...)`, `HankakuToCode[]`/`Zenkaku2Code[]` kana tables — this is the GameCube SDK font/glyph layer (ANSI+SJIS aware), matched against resolved symbols (`GetFontCode = 0x800AD7F0` etc.).
- **Confirmed (symbol+address, game-native text pipeline, `xd-decomp`, no source):** raw SJIS charset tables `sjis_81xx = .rodata:0x802ED348` (size 0x2C90), `sjis_e0xx = .rodata:0x802EFFD8` (size 0x29B0); conversion `SJIStoGSchar__FPUsPc = .text:0x8010B320`, `GScharMakeFromSJIS = 0x80106C8C`; string helpers `GScharCat/Cpy/Cmp/LenCpy`; message-building `GSmsgMakeGScharStr = 0x80105FEC`, `GSmsgGetGSchar/GetCharLength/GetLength`. This "GSchar" format is the game's actual native in-memory text representation — **Confirmed to exist, not Confirmed in exact byte-level format** (no decoder source present, only the function names/addresses that presumably implement one).
- **Build-toolchain fact (Confirmed, not game code):** `configure.py` compiles with `-multibyte` (SJIS-aware) and supports an `sjiswrap` tool, confirming the whole game's text is SJIS-sourced at the build level.
- **Confirmed (`Pokemon-XD-Code`) — directly contradicts an assumption an SJIS-only mental model would make:** the actual in-game dialogue/message character encoding, per this tool's own working string-table reader, is **not** simple Shift-JIS lookup — it's **2 bytes per character, big-endian, raw Unicode code point** (`enums/XGUnicodeCharacters.swift:18-29`), plus an extensive control-character scheme for line breaks, dialogue-end, window-clear, furigana, font/color changes, pauses, and dozens of variable-substitution codes for names (`enums/XGSpecialStringCharacters.swift`). **Reconciling this with `xd-decomp`'s `GSchar`/SJIS-table symbols is an open question** — most likely `GSchar` is an intermediate representation that SJIS source text gets converted *into*, and the final stored/displayed format is the Unicode-codepoint scheme `Pokemon-XD-Code` documents from having actually parsed real string-table data — but this reconciliation has **not been verified by either project as documented**, flagged as Inferred, not Confirmed.
- **Confirmed (`Pokemon-XD-Code`, static file location, XD US, self-describing not hardcoded):** dialogue string table found via `common.rel`'s own internal pointer table, index 136 (`CommonIndexes.StringTable1`).

## Version-scope warning (read before using anything from `Pokemon-XD-Code` against XG)

Every `0x8xxxxxxx`-style address cited above from `Pokemon-XD-Code` is gated in that project's own source code to **region `.US`** (game ID `GXXE`) or, for a few shared items, also Colosseum US (`GC6E`) — confirmed by direct inspection of its `switch region { case .US: ...; default: nil }` pattern used throughout `XDBreakPoints.swift` and `ColoXDGameState.swift`. Critically, **that project's own region detection only checks the game's 4-letter code ("GXXE") from the first 4 bytes of the ISO, not the full 6-character version string ("GXXE01") or any content hash** (`GoDGameInit.swift:74-96,147-164`). This means:

- If XG's ISO header still begins with "GXXE" (plausible for a hack built on top of US XD), a tool built this way would treat it as ordinary XD US and blindly apply these addresses — with no verification that XG's actual code/data layout matches.
- This is exactly the kind of silent-wrong-assumption risk your instructions told me to avoid. **None of these addresses should be trusted against XG until independently re-verified against your actual XG image** (see [FIRST_VERTICAL_SLICE.md](FIRST_VERTICAL_SLICE.md) Phase 0 and [UNKNOWNS_AND_BLOCKERS.md](UNKNOWNS_AND_BLOCKERS.md)).
- They *are* useful as a starting hypothesis/shortlist for the memory-search experiment (e.g. "check whether `0x80814ab6` still behaves like a room ID in XG" is a much faster first probe than a blind scan) — that is their appropriate role at this stage, not as trusted facts.

## Additional platform-relevant finding from `Pokemon-XD-Code`

`Pokemon-XD-Code`'s own live-Dolphin-memory-reading code (`Objects/processes/GoDProcess.swift:9-377`) has three platform branches (`Darwin`, `Linux`/Glibc, and an `#else` catch-all). **The `#else` branch — which covers Windows — is a non-functional stub:** `readVirtualMemory`, `writeVirtualMemory`, `getNextRegion`, and `getRegions` all unconditionally return `nil`/`false`/`[]`. **This specific repo's live-memory tooling does not work on Windows as written.** This does not invalidate Route B in [IMPLEMENTATION_ROUTE_COMPARISON.md](IMPLEMENTATION_ROUTE_COMPARISON.md) — the recommended `dolphin-memory-engine`/`py-dolphin-memory-engine` tooling is a separate, Windows-native implementation (using Windows' own process-memory APIs, not the POSIX-style approach this Swift repo stubbed out) — but it is a concrete reason not to try to reuse `Pokemon-XD-Code`'s Dolphin-process code directly on this machine.
